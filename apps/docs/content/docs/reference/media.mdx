---
title: Media
description: Upload, serve, and manage assets via cms.api.media.
---

Media methods live under `cms.api.media` and are mirrored on the client as `client.media.<method>` with identical types. For the model behind them, see the [Media concept](/docs/concepts/media).

Every method requires a session except the [`asset`](#public-delivery) delivery gate. Uploaded assets are created `private`; publishing referencing content or `updateAssetsStatus` makes them `public`. Each asset row carries `deliveryUrl`, the gate path to render, and `url`, the direct object URL (`${publicUrl}/${objectKey}`), which is `null` for private assets.

## Folders

### List Folders [#listfolders]

Walk the folder tree one level at a time. Omit `parentFolderId` to get the root-level folders, or pass a folder id to get that folder's direct children — sorted by name. It's intentionally unpaginated: each call is bounded by a single parent's direct-child fan-out, so you page the tree by descending, not by offset.

<APIMethod
  method="GET"
  path="/media/listFolders"
  fn="listFolders"
  collection="media"
  resource="media"
  operation="read"
  args={`{
  query: { parentFolderId: 'fld_images' }, // omit for the root-level folders
}`}
  returns={{
    folders: { type: '{ id, name, parentId, createdBy, createdAt, assetCount, assetCountRecursive }[]', description: 'The live child folders (of the parent, or of the root), sorted by name. `assetCount` counts live original assets directly in the folder, `assetCountRecursive` those in its whole subtree, both within scope.' },
  }}
  params={{
    parentFolderId: { type: 'string', description: 'Parent folder id. Omit for the root-level folders (those with no parent).' },
  }}
/>

### Delete a Folder [#deletefolder]

Move a folder to the trash. Folders never cascade: pick what happens to the content with `mode`, and preview the effect with `dryRun`.

- `empty-only` (default): only a folder without live assets or subfolders; otherwise `FOLDER_HAS_CONTENT`.
- `move-to-parent`: subfolders and assets move one level up; `FOLDER_NAME_TAKEN` when a subfolder's name exists there.
- `archive-contents`: the whole subtree goes to the trash; assets in use (or suspected in rich text) are skipped and moved to the parent instead.

<APIMethod
  method="POST"
  path="/media/deleteFolder"
  fn="deleteFolder"
  collection="media"
  resource="media"
  operation="delete"
  args={`{
  body: {
    folderId: 'fld_images', // required
    mode: 'archive-contents',
    dryRun: true,
  },
}`}
  returns={{
    folderId: { type: 'string', description: 'The folder.' },
    folders: { type: 'number', description: 'Live subfolders in its subtree.' },
    assets: { type: 'number', description: 'Live original assets in its subtree.' },
    assetsInUse: { type: 'number', description: 'How many of those are referenced by live content.' },
    skipped: { type: 'string[]', description: 'Asset ids `archive-contents` kept (in use or suspected in rich text); empty otherwise.' },
  }}
  params={{
    folderId: { type: 'string', required: true, description: 'The folder to delete.' },
    mode: { type: "'empty-only' | 'move-to-parent' | 'archive-contents'", description: 'What happens to the content. Default `empty-only`.' },
    dryRun: { type: 'boolean', description: 'Return the counts without changing anything.' },
  }}
/>

## Uploads

### Create a Signed Upload [#createsignedupload]

Hand the browser presigned PUT URLs so it can upload files straight to your bucket — no bytes pass through your server. Nothing is written to the database here: each entry carries a signed `token`, and the asset row is created by [`completeUpload`](#completeupload) once the PUT has landed. PUT each file to its `signedUrl` with the returned `headers`, pass the tokens to `completeUpload`, then flip the assets to `public` when you're ready to serve them. New uploads are stored at the object key `<id>/<slug>`.

<APIMethod
  method="POST"
  path="/media/createSignedUpload"
  fn="createSignedUpload"
  collection="media"
  resource="media"
  operation="create"
  args={`{
  body: {
    files: [{ name: 'hero.jpg', size: 512000, type: 'image/jpeg' }], // required
  },
}`}
  returns={{
    uploads: { type: '{ id, objectKey, url, signedUrl, headers, token }[]', description: 'One entry per file: the asset id and object key it will get, its presigned `signedUrl`, the `headers` to send with the PUT, and the `token` to pass to `completeUpload`.' },
    expiresAt: { type: 'Date', description: 'When the signed URLs expire.' },
  }}
  params={{
    files: { type: '{ name: string; size: number; type: string; variantOf?: string }[]', required: true, description: 'Files to upload (at least one). `size` is the byte length, `type` a MIME type, `variantOf` an existing asset id when uploading a variant.' },
    folderId: { type: 'string', description: 'Target folder id.' },
  }}
/>

Returns `{ uploads: { id, objectKey, url, deliveryUrl, signedUrl, headers, token }[], expiresAt }`. `url` is `null` (new assets are private); `deliveryUrl` is the gate path. PUT each file to its `signedUrl` with the returned `headers` (`Content-Type`, `Cache-Control`); `expiresAt` is when the signed URLs expire. The token stays valid for one hour past `expiresAt`, so a PUT that started before expiry can still be completed. Throws `TOO_MANY_FILES`, `FILE_TOO_LARGE`, `INVALID_FILE_TYPE`, `FOLDER_NOT_FOUND`, or `ASSET_NOT_FOUND` (unknown `variantOf`).

### Complete an Upload [#completeupload]

Create the asset rows for the files the browser PUT to the URLs from `createSignedUpload`. For each token the CMS checks the signature, the calling user and scope, `HEAD`s the object (its length must equal and its content type must match the declared file), sniffs the leading bytes of a declared image against its magic bytes, mints the slug, and inserts the row as `private`. An object that fails the length, type, or sniff check is deleted from the bucket. Completing the same token twice returns the existing asset. One file's failure never fails the call: it is reported per entry in `errors`.

<APIMethod
  method="POST"
  path="/media/completeUpload"
  fn="completeUpload"
  collection="media"
  resource="media"
  operation="create"
  args={`{
  body: {
    uploads: signed.uploads.map(({ token }) => ({ token })), // required
  },
}`}
  returns={{
    assets: { type: 'AssetListItem[]', description: 'The created assets, with the same fields a `listAssets` row carries.' },
    errors: { type: '{ index: number; code: string; message: string }[]', description: 'One entry per rejected token; `index` is its position in `uploads`.' },
  }}
  params={{
    uploads: { type: '{ token: string }[]', required: true, description: 'The tokens from `createSignedUpload`, at least one and at most `maxFiles`.' },
  }}
/>

Returns `{ assets, errors }`. Per-entry `code` is one of `UPLOAD_TOKEN_INVALID` (malformed, expired, or minted for another user or tenant), `UPLOAD_NOT_FOUND` (no object at the key: the PUT never completed), `VALIDATION_ERROR` (the object's length or content type differs from the declared file), `INVALID_FILE_TYPE` (the bytes contradict the declared image type), `FOLDER_NOT_FOUND` or `ASSET_NOT_FOUND` (the folder or `variantOf` target was removed after presign, or the asset from an earlier completion of this token was archived), `UPLOAD_FAILED` (the bucket answered the object check with an error), or `SLUG_GENERATION_FAILED`.

```ts
// Full browser-side upload flow (the `useUploadAssets` hook does this for you).
const signed = await cmsClient.media.createSignedUpload({
  body: { files: [{ name: file.name, size: file.size, type: file.type }] },
});
await fetch(signed.uploads[0].signedUrl, {
  method: 'PUT',
  headers: signed.uploads[0].headers,
  body: file,
});
const { assets, errors } = await cmsClient.media.completeUpload({
  body: { uploads: [{ token: signed.uploads[0].token }] },
});
```

### Upload Assets [#uploadassets]

Upload file bytes through the server — reach for this for small files or server-initiated uploads. It takes the same shape as `createSignedUpload`, but each file carries its `buffer`. Declared image types are sniffed against their magic bytes, so a spoofed file (e.g. an SVG posing as `image/png`) is rejected before any row or object is written.

<Callout type="warn">
  `uploadAssets` takes in-process bytes (`buffer: Blob | ArrayBuffer`) and is **server-side only**, for the same reason as [`replaceAsset`](#replaceasset) below: a browser `File` can't survive the client's JSON request body. It's marked `scope: 'server'`, so `client.media.uploadAssets` is a compile error, not just a runtime failure — the client's types never offer it. Browsers must use [`createSignedUpload`](#createsignedupload) instead. `cms.api.media.uploadAssets` is unaffected; this is a client-side type filter only.
</Callout>

<APIMethod
  method="POST"
  path="/media/uploadAssets"
  fn="uploadAssets"
  collection="media"
  resource="media"
  operation="create"
  args={`{
  body: {
    files: [{ name: 'hero.jpg', size: buffer.byteLength, type: 'image/jpeg', buffer }], // required
  },
}`}
  returns={{
    assets: { type: 'AssetListItem[]', description: 'The uploaded assets, each with the same fields a `listAssets` row carries.' },
  }}
  params={{
    files: { type: '{ name: string; size: number; type: string; buffer: Blob | ArrayBuffer; variantOf?: string }[]', required: true, description: 'Files with byte content (at least one). The real byte length is measured server-side; the declared `size` is not trusted.' },
    folderId: { type: 'string', description: 'Target folder id.' },
  }}
/>

Returns `{ assets }`, each with the same fields a `listAssets` row carries. Throws `TOO_MANY_FILES`, `FILE_TOO_LARGE`, `INVALID_FILE_TYPE`, `FOLDER_NOT_FOUND`, `ASSET_NOT_FOUND` (unknown `variantOf`), `UPLOAD_FAILED`, or `SLUG_GENERATION_FAILED`.

### Replace an Asset [#replaceasset]

Swap the bytes behind an existing asset while keeping its `id` (and `folderId`/`status`) stable, so every content reference picks up the new image with no content change — the id-addressed gate re-resolves it. A fresh slug and object key are minted for a clean cache-bust, and the asset's old variants are archived (regenerate them afterward). Server-side and atomic.

<Callout type="warn">
  `replaceAsset` takes in-process bytes (`buffer: Blob | ArrayBuffer`) and is for **server-side callers only** — a browser `File` cannot survive the client's JSON request body (it serializes to `{}`). It's marked `scope: 'server'`, so `client.media.replaceAsset` is a compile error, not just a runtime failure — the client's types never offer it. Browsers must use [`createSignedReplace`](#createsignedreplace) + [`commitReplace`](#commitreplace) instead, or the `useReplaceAsset` client hook that wraps them. `cms.api.media.replaceAsset` is unaffected; this is a client-side type filter only.
</Callout>

<APIMethod
  method="POST"
  path="/media/replaceAsset"
  fn="replaceAsset"
  collection="media"
  resource="media"
  operation="update"
  args={`{
  body: {
    assetId: 'ast_123', // required
    file: { name: 'hero.jpg', size: buffer.byteLength, type: 'image/jpeg', buffer }, // required
  },
}`}
  returns={{
    asset: { type: 'AssetListItem', description: 'The updated asset (same `id`, new `slug`/`objectKey`/`url`), with the same fields a `listAssets` row carries.' },
  }}
  params={{
    assetId: { type: 'string', required: true, description: 'The asset to replace.' },
    file: { type: '{ name: string; size: number; type: string; buffer: Blob | ArrayBuffer }', required: true, description: 'The new file bytes. Sniffed like `uploadAssets`. Server-side only — see the callout above.' },
  }}
/>

Returns `{ asset }` with the same fields a `listAssets` row carries. Throws `CANNOT_REPLACE_VARIANT` (target is itself a variant), `ASSET_NOT_FOUND`, `FILE_TOO_LARGE` / `INVALID_FILE_TYPE`, or `UPLOAD_FAILED` (asset left unchanged).

### Create a Signed Replace [#createsignedreplace]

The browser-callable half of a replace: validates the target asset (live, in scope, not itself a variant) and the new file's declared metadata, mints a new slug and object key (`<fresh id>/<slug>`), and returns a presigned PUT URL plus a signed `token` — the same shape as `createSignedUpload`, but for an *existing* asset. It does **not** touch the database; call [`commitReplace`](#commitreplace) with the token once the PUT succeeds.

<APIMethod
  method="POST"
  path="/media/createSignedReplace"
  fn="createSignedReplace"
  collection="media"
  resource="media"
  operation="update"
  args={`{
  body: {
    assetId: 'ast_123', // required
    file: { name: 'hero-v2.jpg', size: file.size, type: file.type }, // required
  },
}`}
  returns={{
    assetId: { type: 'string', description: 'Echoes the requested asset id.' },
    slug: { type: 'string', description: 'The freshly minted slug (cache-bust) the row will carry after `commitReplace`.' },
    objectKey: { type: 'string', description: 'The freshly minted object key (`<fresh id>/<slug>`).' },
    url: { type: 'string | null', description: "The object's direct URL once `commitReplace` repoints the row; `null` for a private asset." },
    deliveryUrl: { type: 'string', description: 'The gate path of the asset.' },
    signedUrl: { type: 'string', description: 'Presigned PUT URL — upload the new bytes here.' },
    headers: { type: 'Record<string, string>', description: 'Headers to send with the PUT (`Content-Type`, `Cache-Control`).' },
    expiresAt: { type: 'Date', description: 'When the signed URL expires.' },
    token: { type: 'string', description: 'Signed token binding the asset, object key, slug, type, size, user and scope. Pass it to `commitReplace`.' },
  }}
  params={{
    assetId: { type: 'string', required: true, description: 'The asset to replace.' },
    file: { type: '{ name: string; size: number; type: string }', required: true, description: "The new file's declared metadata — no bytes; the browser PUTs them straight to your bucket." },
  }}
/>

Throws `ASSET_NOT_FOUND` (missing, archived, or out of scope), `CANNOT_REPLACE_VARIANT`, `FILE_TOO_LARGE` / `INVALID_FILE_TYPE`, or `SLUG_GENERATION_FAILED`.

### Commit a Replace [#commitreplace]

Repoints the asset's row at the new object after the browser's PUT to `createSignedReplace`'s `signedUrl` has succeeded — the second half of the browser-callable replace flow. The token names the asset, object key, slug, type and size, and must have been minted for the calling user and scope. Before anything is written the object is `HEAD`ed (its length must equal and its content type must match the token) and a declared image is sniffed against its magic bytes; a mismatching object is deleted. Atomic and TOCTOU-safe like `replaceAsset`: the row is repointed and old variants archived in one transaction, and it keeps every guarantee `replaceAsset` has (including tombstoning the superseded object so it becomes reclaimable — see [Object lifecycle](/docs/concepts/media#object-lifecycle)).

<APIMethod
  method="POST"
  path="/media/commitReplace"
  fn="commitReplace"
  collection="media"
  resource="media"
  operation="update"
  args={`{
  body: {
    token: signed.token, // required — from createSignedReplace
  },
}`}
  returns={{
    asset: { type: 'AssetListItem', description: 'The updated asset (same `id`, new `slug`/`objectKey`/`url`), with the same fields a `listAssets` row carries.' },
  }}
  params={{
    token: { type: 'string', required: true, description: 'The `token` returned by `createSignedReplace`.' },
  }}
/>

Returns `{ asset }` with the same fields a `listAssets` row carries. Committing the same token twice returns the already-repointed asset. Throws `UPLOAD_TOKEN_INVALID` (malformed, expired, or minted for another user or tenant), `UPLOAD_NOT_FOUND` (no object at the token's key: the PUT never completed), `FILE_TOO_LARGE` / `INVALID_FILE_TYPE` / `TOO_MANY_FILES` (the token's type or size fails the media config as it is at commit time, or the bytes contradict the declared image type), `VALIDATION_ERROR` (the object's length or content type differs from the token), or `ASSET_NOT_FOUND` if the asset was archived or left scope since `createSignedReplace` (TOCTOU) — the row is left unchanged and the just-uploaded object is tombstoned for reclaim rather than abandoned.

```ts
// Full browser-side replace flow.
const signed = await cmsClient.media.createSignedReplace({
  body: { assetId: hero.id, file: { name: file.name, size: file.size, type: file.type } },
});
await fetch(signed.signedUrl, { method: 'PUT', headers: signed.headers, body: file });
const { asset } = await cmsClient.media.commitReplace({
  body: { token: signed.token },
});
```

The React client wraps this pipeline as `client.media.useReplaceAsset()` (mirrors `useUploadAssets`) — `const { replace, isReplacing, progress, error, result } = client.media.useReplaceAsset(); await replace(assetId, file);`. The vanilla client exposes the same state as a raw nanostores atom at `client.media.replaceState`.

### Move Assets [#moveassets]

Move a batch of assets into a folder (or to the root with `folderId: null`). Non-existent, out-of-scope, archived, and variant ids are skipped (surfaced in `skipped`), so a batch partially succeeds. A moved asset's variants follow it into the same folder, so an original and its variants are never split apart.

<APIMethod
  method="POST"
  path="/media/moveAssets"
  fn="moveAssets"
  collection="media"
  resource="media"
  operation="update"

## Public delivery

### Serve an Asset [#asset]

Address an asset by its **id** (what content stores); the gate `302`s to the asset's current object. It's what you put behind an `<img src>`, and it survives a `replaceAsset` untouched: the gate re-resolves the id to the current object. A public asset redirects to its object URL, short-cached (`max-age=300`, not immutable), so swapping the object behind the same id propagates automatically. A private asset redirects to a signed GET valid for at most 300 seconds with `Cache-Control: private, no-store`, and only for a caller your `authMiddleware` accepts for `media` / `read`; anonymous callers get `ASSET_ACCESS_DENIED`. With a scoping plugin, ids outside the caller's scope answer `ASSET_NOT_FOUND`.

<APIMethod
  method="GET"
  path="/media/asset/{assetId}"
  fn="asset"
  collection="media"
  public
  args={`{
  params: { assetId: 'ast_123' }, // required
  query: { w: 800, format: 'webp' },
}`}
  returns={{
    Location: { type: '302 redirect', description: "A `302` (short-cached, `max-age=300`) to the asset's public object URL for raster images (PNG, JPEG, GIF, WebP, AVIF), video, audio and PDF, or, for `download=true` and every other type, to a signed object URL valid for one hour whose `response-content-disposition=attachment` makes the bucket answer with a download. No JSON body: the browser follows the `Location` header to the bytes." },
  }}
  params={{
    assetId: { type: 'string', required: true, description: 'Path parameter: the asset id to serve.' },
    format: { type: "'webp' | 'jpeg' | 'png'", description: 'Serve a pre-uploaded format variant, falling back to the original.' },
    w: { type: 'number', description: 'Serve a pre-uploaded width variant (positive integer), falling back to the original.' },
    download: { type: 'boolean', description: 'Set `true` to redirect to a signed URL that forces a download (`Content-Disposition: attachment`, filename = the asset slug) instead of the public object URL.' },
  }}
/>
