---
title: Media
description: Upload, serve, and manage assets via cms.api.media.
---

Media methods live under `cms.api.media` and are mirrored on the client as `client.media.<method>` with identical types. For the model behind them, see the [Media concept](/docs/concepts/media).

Every method requires a session except the public [`asset`](#public-delivery) delivery redirect. Uploaded assets are created `private`; flip them to `public` with `updateAssetsStatus` before serving. Each asset row carries a direct object `url` (`${publicUrl}/${objectKey}`) for internal/admin display such as a media library; serve assets in content through the [public delivery](#public-delivery) gate instead.

## Folders

### List Folders [#listfolders]

Walk the folder tree one level at a time. Omit `parentFolderId` to get the root-level folders, or pass a folder id to get that folder's direct children — sorted by name. It's intentionally unpaginated: each call is bounded by a single parent's direct-child fan-out, so you page the tree by descending, not by offset.

<APIMethod
  method="GET"
  path="/media/listFolders"
  fn="listFolders"
  collection="media"
  resource="media"
  operation="read"
  args={`{
  query: { parentFolderId: 'fld_images' }, // omit for the root-level folders
}`}
  returns={{
    folders: { type: '{ id, name, parentId, createdBy, createdAt }[]', description: 'The direct child folders (of the parent, or of the root), sorted by name. `parentId` and `createdBy` are `null` at the root or when unknown.' },
  }}
  params={{
    parentFolderId: { type: 'string', description: 'Parent folder id. Omit for the root-level folders (those with no parent).' },
  }}
/>

## Assets

### List Assets [#listassets]

List the assets in your media library, with optional filtering (by folder, status, or slug search) and sorting. For paging, prefer the stable `cursor` (keyset) mode to walk the whole library — pass the previous page's `nextCursor` to continue; the legacy `offset` mode is capped to the first 100 rows and `cursor` takes precedence over it.

<APIMethod
  method="GET"
  path="/media/listAssets"
  fn="listAssets"
  collection="media"
  resource="media"
  operation="read"
  args={`{
  query: {
    status: 'public',
    limit: 50,
  },
}`}
  returns={{
    assets: { type: 'AssetListItem[]', description: 'The assets on this page. Each carries `id`, `slug`, `mimeType`, `size`, `objectKey`, direct `url`, `status`, `folderId`, `variantOf`, `uploadedBy`, `createdAt`, `updatedAt`.' },
    total: { type: 'number', description: 'Total assets across all pages for the current filter (ignores paging).' },
    hasMore: { type: 'boolean', description: 'Whether more assets exist after this page.' },
    nextCursor: { type: 'string | null', description: 'Opaque cursor for the next page; `null` at the end of the list. Pass it back as `cursor` to continue.' },
  }}
  params={{
    folderId: { type: 'string', description: "Filter to a folder's assets. Omit for no folder filter." },
    unfiled: { type: 'boolean', description: 'Set `true` to list only root-level (unfiled) assets, those with no folder. Takes precedence over `folderId`.' },
    status: { type: "'private' | 'public'", description: 'Filter by privacy status.' },
    search: { type: 'string', description: 'Case-insensitive substring match against the asset slug.' },
    limit: { type: 'number', default: '20', description: 'Page size, 1 to 100.' },
    offset: { type: 'number', default: '0', description: 'Rows to skip. Ignored when `cursor` is given.' },
    cursor: { type: 'string', description: "Opaque keyset cursor from a previous page's `nextCursor`; pages past the offset ceiling." },
    sortBy: { type: "'createdAt' | 'slug' | 'size'", default: "'createdAt'", description: 'Sort field.' },
    sortDirection: { type: "'asc' | 'desc'", default: "'desc'", description: 'Sort order.' },
  }}
/>

Each asset includes the direct `url` (`${publicUrl}/${objectKey}`) for internal/admin display; `nextCursor` is `null` at the end of the list.

### Get Assets by Id [#getassets]

Resolve a batch of assets by id — the id-to-asset counterpart to `listAssets`, for previewing assets that fall outside the current library page (say, ones referenced by content you're editing). You get back the same row shape as `listAssets`; archived, out-of-scope, and unknown ids are simply absent from the result (no error), and order is not guaranteed.

<APIMethod

  }}
  params={{
    ids: { type: 'string[]', required: true, description: 'Asset ids to resolve (at least one).' },
  }}
/>

## Uploads

### Create a Signed Upload [#createsignedupload]

Hand the browser presigned PUT URLs so it can upload files straight to your bucket — no bytes pass through your server. The asset rows are created up front as `private`; PUT each file to its `signedUrl` with the returned `headers`, then flip the assets to `public` when you're ready to serve them.

<APIMethod
  method="POST"
  path="/media/createSignedUpload"
  fn="createSignedUpload"
  collection="media"
  resource="media"
  operation="create"
  args={`{
  body: {
    files: [{ name: 'hero.jpg', size: 512000, type: 'image/jpeg' }], // required
  },
}`}
  returns={{
    assets: { type: '{ id, slug, objectKey, url, signedUrl, headers }[]', description: 'One entry per file: the created (private) asset plus its presigned `signedUrl` and the `headers` to send with the PUT.' },
    expiresAt: { type: 'Date', description: 'When the signed URLs expire.' },
  }}
  params={{
    files: { type: '{ name: string; size: number; type: string; variantOf?: string }[]', required: true, description: 'Files to upload (at least one). `size` is the byte length, `type` a MIME type, `variantOf` an existing asset id when uploading a variant.' },
    folderId: { type: 'string', description: 'Target folder id.' },
  }}
/>

Returns `{ assets: { id, slug, objectKey, url, signedUrl, headers }[], expiresAt }`. PUT each file to its `signedUrl` with the returned `headers` (`Content-Type`, `x-amz-acl: public-read`); `expiresAt` is when the signed URLs expire. Throws `TOO_MANY_FILES`, `FILE_TOO_LARGE`, `INVALID_FILE_TYPE`, `FOLDER_NOT_FOUND`, `ASSET_NOT_FOUND` (unknown `variantOf`), or `SLUG_GENERATION_FAILED`.

### Upload Assets [#uploadassets]

Upload file bytes through the server — reach for this for small files or server-initiated uploads. It takes the same shape as `createSignedUpload`, but each file carries its `buffer`. Declared image types are sniffed against their magic bytes, so a spoofed file (e.g. an SVG posing as `image/png`) is rejected before any row or object is written.

<APIMethod
  method="POST"
  path="/media/uploadAssets"
  fn="uploadAssets"
  collection="media"
  resource="media"
  operation="create"
  args={`{
  body: {
    files: [{ name: 'hero.jpg', size: buffer.byteLength, type: 'image/jpeg', buffer }], // required
  },
}`}
  returns={{
    assets: { type: 'AssetListItem[]', description: 'The uploaded assets, each with the same fields a `listAssets` row carries.' },
  }}
  params={{
    files: { type: '{ name: string; size: number; type: string; buffer: Blob | ArrayBuffer; variantOf?: string }[]', required: true, description: 'Files with byte content (at least one). The real byte length is measured server-side; the declared `size` is not trusted.' },
    folderId: { type: 'string', description: 'Target folder id.' },
  }}
/>

Returns `{ assets }`, each with the same fields a `listAssets` row carries. Throws `TOO_MANY_FILES`, `FILE_TOO_LARGE`, `INVALID_FILE_TYPE`, `FOLDER_NOT_FOUND`, `ASSET_NOT_FOUND` (unknown `variantOf`), `UPLOAD_FAILED`, or `SLUG_GENERATION_FAILED`.

### Replace an Asset [#replaceasset]

Swap the bytes behind an existing asset while keeping its `id` (and `folderId`/`status`) stable, so every content reference picks up the new image with no content change — the id-addressed gate re-resolves it. A fresh slug and object key are minted for a clean cache-bust, and the asset's old variants are archived (regenerate them afterward). Server-side and atomic.

<Callout type="warn">
  `replaceAsset` takes in-process bytes (`buffer: Blob | ArrayBuffer`) and is for **server-side callers only** — a browser `File` cannot survive the client's JSON request body (it serializes to `{}`), so a browser call to `replaceAsset` type-checks but fails at runtime. Browsers must use [`createSignedReplace`](#createsignedreplace) + [`commitReplace`](#commitreplace) instead, or the `useReplaceAsset` client hook that wraps them.
</Callout>

<APIMethod
  method="POST"
  path="/media/replaceAsset"
  fn="replaceAsset"
  collection="media"
  resource="media"
  operation="update"
  args={`{
  body: {
    assetId: 'ast_123', // required
    file: { name: 'hero.jpg', size: buffer.byteLength, type: 'image/jpeg', buffer }, // required
  },
}`}
  returns={{
    asset: { type: 'AssetListItem', description: 'The updated asset (same `id`, new `slug`/`objectKey`/`url`), with the same fields a `listAssets` row carries.' },
  }}
  params={{
    assetId: { type: 'string', required: true, description: 'The asset to replace.' },
    file: { type: '{ name: string; size: number; type: string; buffer: Blob | ArrayBuffer }', required: true, description: 'The new file bytes. Sniffed like `uploadAssets`. Server-side only — see the callout above.' },
  }}
/>

Returns `{ asset }` with the same fields a `listAssets` row carries. Throws `CANNOT_REPLACE_VARIANT` (target is itself a variant), `ASSET_NOT_FOUND`, `FILE_TOO_LARGE` / `INVALID_FILE_TYPE`, or `UPLOAD_FAILED` (asset left unchanged).

### Create a Signed Replace [#createsignedreplace]

The browser-callable half of a replace: validates the target asset (live, in scope, not itself a variant) and the new file's declared metadata, mints a new slug/object key, and returns a presigned PUT URL — the same shape as `createSignedUpload`, but for an *existing* asset. It does **not** touch the database; call [`commitReplace`](#commitreplace) once the PUT succeeds.

<APIMethod
  method="POST"
  path="/media/createSignedReplace"
  fn="createSignedReplace"
  collection="media"
  resource="media"
  operation="update"
  args={`{
  body: {
    assetId: 'ast_123', // required
    file: { name: 'hero-v2.jpg', size: file.size, type: file.type }, // required
  },
}`}
  returns={{
    assetId: { type: 'string', description: 'Echoes the requested asset id — pass it through to `commitReplace`.' },
    slug: { type: 'string', description: 'The freshly minted slug (cache-bust). Pass it through to `commitReplace`.' },
    objectKey: { type: 'string', description: 'The freshly minted object key (equal to `slug`). Pass it through to `commitReplace`.' },
    url: { type: 'string', description: "The object's public URL once the PUT below succeeds AND `commitReplace` repoints the row. For internal/admin display only." },
    signedUrl: { type: 'string', description: 'Presigned PUT URL — upload the new bytes here.' },
    headers: { type: 'Record<string, string>', description: 'Headers to send with the PUT (`Content-Type`, `x-amz-acl: public-read`).' },
    expiresAt: { type: 'Date', description: 'When the signed URL expires.' },
  }}
  params={{
    assetId: { type: 'string', required: true, description: 'The asset to replace.' },
    file: { type: '{ name: string; size: number; type: string }', required: true, description: "The new file's declared metadata — no bytes; the browser PUTs them straight to your bucket." },
  }}
/>

Throws `ASSET_NOT_FOUND` (missing, archived, or out of scope), `CANNOT_REPLACE_VARIANT`, `FILE_TOO_LARGE` / `INVALID_FILE_TYPE`, or `SLUG_GENERATION_FAILED`.

### Commit a Replace [#commitreplace]

Repoints the asset's row at the new object after the browser's PUT to `createSignedReplace`'s `signedUrl` has succeeded — the second half of the browser-callable replace flow. Atomic and TOCTOU-safe like `replaceAsset`: the row is repointed and old variants archived in one transaction, and it keeps every guarantee `replaceAsset` has (including tombstoning the superseded object so it becomes reclaimable — see [Object lifecycle](/docs/concepts/media#object-lifecycle)).

<APIMethod
  method="POST"
  path="/media/commitReplace"
  fn="commitReplace"
  collection="media"
  resource="media"
  operation="update"
  args={`{
  body: {
    assetId: 'ast_123', // required
    objectKey: signed.objectKey, // required — from createSignedReplace
    slug: signed.slug, // required — from createSignedReplace
    mimeType: file.type, // required
    size: file.size, // required
  },
}`}
  returns={{
    asset: { type: 'AssetListItem', description: 'The updated asset (same `id`, new `slug`/`objectKey`/`url`), with the same fields a `listAssets` row carries.' },
  }}
  params={{
    assetId: { type: 'string', required: true, description: 'The asset being replaced (must match the `createSignedReplace` call).' },
    objectKey: { type: 'string', required: true, description: 'The `objectKey` returned by `createSignedReplace`.' },
    slug: { type: 'string', required: true, description: 'The `slug` returned by `createSignedReplace`.' },
    mimeType: { type: 'string', required: true, description: "The uploaded file's declared MIME type." },
    size: { type: 'number', required: true, description: "The uploaded file's declared byte size." },
  }}
/>

Returns `{ asset }` with the same fields a `listAssets` row carries. Throws `ASSET_NOT_FOUND` if the asset was archived or left scope since `createSignedReplace` (TOCTOU) — the row is left unchanged and the just-uploaded object is tombstoned for reclaim rather than abandoned.

```ts
// Full browser-side replace flow.
const signed = await cmsClient.media.createSignedReplace({
  body: { assetId: hero.id, file: { name: file.name, size: file.size, type: file.type } },
});
await fetch(signed.signedUrl, { method: 'PUT', headers: signed.headers, body: file });
const { asset } = await cmsClient.media.commitReplace({
  body: {
    assetId: hero.id,
    objectKey: signed.objectKey,
    slug: signed.slug,
    mimeType: file.type,
    size: file.size,
  },
});
```

The React client wraps this pipeline as `client.media.useReplaceAsset()` (mirrors `useUploadAssets`) — `const { replace, isReplacing, progress, error, result } = client.media.useReplaceAsset(); await replace(assetId, file);`. The vanilla client exposes the same state as a raw nanostores atom at `client.media.replaceState`.

### Move Assets [#moveassets]

Move a batch of assets into a folder (or to the root with `folderId: null`). Non-existent, out-of-scope, archived, and variant ids are skipped (surfaced in `skipped`), so a batch partially succeeds. A moved asset's variants follow it into the same folder, so an original and its variants are never split apart.

<APIMethod

  },
}`}

/>

Throws `FOLDER_NOT_FOUND` (unknown/out-of-scope target) or `ASSET_NOT_FOUND` (no live ids).

## Public delivery

### Serve an Asset [#asset]

Serve an asset on a public page by addressing it by **asset id** (what content stores) — this `302`s to the asset's current object URL. It's what you put behind an `<img src>`, and it survives a `replaceAsset` untouched: the gate just re-resolves the id to the current object. Private assets are rejected with `ASSET_ACCESS_DENIED`, and the redirect is short-cached (`max-age=300`, not immutable), so swapping the object behind the same id propagates automatically.

<APIMethod
  method="GET"
  path="/media/asset/{assetId}"
  fn="asset"
  collection="media"
  public
  args={`{
  params: { assetId: 'ast_123' }, // required
  query: { w: 800, format: 'webp' },
}`}
  returns={{
    Location: { type: '302 redirect', description: "A `302` to the asset's public object URL (short-cached, `max-age=300`). No JSON body: the browser follows the `Location` header to the bytes." },
  }}
  params={{
    assetId: { type: 'string', required: true, description: 'Path parameter: the asset id to serve.' },
    format: { type: "'webp' | 'jpeg' | 'png'", description: 'Serve a pre-uploaded format variant, falling back to the original.' },
    w: { type: 'number', description: 'Serve a pre-uploaded width variant (positive integer), falling back to the original.' },
    download: { type: 'boolean', description: 'Set `true` to send a `Content-Disposition: attachment` header.' },
  }}
/>
