---
title: Media
description: Upload, serve, and manage assets via cms.api.media.
---

Media methods live under `cms.api.media` and are mirrored on the client as `client.media.<method>` with identical types. For the model behind them, see the [Media concept](/docs/concepts/media).

Every method requires a session except the [`asset`](#public-delivery) delivery gate. Uploaded assets are created `private`; publishing referencing content or `updateAssetsStatus` makes them `public`. Each asset row carries `deliveryUrl`, the gate path to render, and `url`, the direct object URL (`${publicUrl}/${objectKey}`), which is `null` for private assets.

## Folders

### List Folders [#listfolders]

Walk the folder tree one level at a time. Omit `parentFolderId` to get the root-level folders, or pass a folder id to get that folder's direct children — sorted by name. It's intentionally unpaginated: each call is bounded by a single parent's direct-child fan-out, so you page the tree by descending, not by offset.

<APIMethod
  method="GET"
  path="/media/listFolders"
  fn="listFolders"
  collection="media"
  resource="media"
  operation="read"
  args={`{
  query: { parentFolderId: 'fld_images' }, // omit for the root-level folders
}`}
  returns={{
    folders: { type: '{ id, name, parentId, createdBy, createdAt, folderCount, assetCount, assetCountRecursive }[]', description: 'The live child folders (of the parent, or of the root), sorted by name. `folderCount` counts live direct subfolders (a tree shows a disclosure only when it is above 0), `assetCount` live original assets directly in the folder, `assetCountRecursive` those in its whole subtree, both within scope.' },
  }}
  params={{
    parentFolderId: { type: 'string', description: 'Parent folder id. Omit for the root-level folders (those with no parent).' },
  }}
/>

### Delete a Folder [#deletefolder]

Move a folder to the trash. Folders never cascade: pick what happens to the content with `mode`, and preview the effect with `dryRun`.

- `empty-only` (default): only a folder without live assets or subfolders; otherwise `FOLDER_HAS_CONTENT`.
- `move-to-parent`: subfolders and assets move one level up; `FOLDER_NAME_TAKEN` when a subfolder's name exists there.
- `archive-contents`: the whole subtree goes to the trash; assets in use (or suspected in rich text) are skipped and moved to the parent instead.

<APIMethod

  path="/media/deleteFolder"
  fn="deleteFolder"
  collection="media"
  resource="media"
  operation="delete"
  args={`{
  body: {
    folderId: 'fld_images', // required
    mode: 'archive-contents',
    dryRun: true,
  },
}`}
  returns={{
    folderId: { type: 'string', description: 'The folder.' },
    folders: { type: 'number', description: 'Live subfolders in its subtree.' },
    assets: { type: 'number', description: 'Live original assets in its subtree.' },
    assetsInUse: { type: 'number', description: 'How many of those are referenced by live content.' },
    pages: { type: 'number', description: 'Distinct roots (pages) using those assets, for a confirmation such as "9 are used on 14 pages".' },
    skipped: { type: 'string[]', description: 'Asset ids `archive-contents` kept (in use or suspected in rich text); empty otherwise.' },
  }}
  params={{
    folderId: { type: 'string', required: true, description: 'The folder to delete.' },
    mode: { type: "'empty-only' | 'move-to-parent' | 'archive-contents'", description: 'What happens to the content. Default `empty-only`.' },

## Assets

### List Assets [#listassets]

List the original assets of the library (never variants or revisions), filtered on the server so paging stays exact. `q` searches file name (weighted highest), description, credit and copyright through a full-text index and also matches substrings of the file name and slug, so `Hamb` finds `Hamburg Hafen.jpg`. For paging, prefer the stable `cursor` (keyset) mode: pass the previous page's `nextCursor` to continue; the legacy `offset` mode is capped to the first 100 rows and `cursor` takes precedence over it. Counting a large filtered set is expensive, so pass `includeTotal: false` when you page and do not need `total` (it is then `null`).

### Replace an Asset Everywhere [#replaceassetusages]

Swap one asset for another in all content: one commit per root and branch head (`Replace asset <from> with <to>`) through the normal commit pipeline. A branch the branch policy protects fails with its error code while the others go on. Usages found in text (asset URLs) are not rewritten; `notRewritten` counts them. Collection hooks do not run. Unlike [`replaceAsset`](#replaceasset), which keeps the id and swaps the bytes, this changes content, so it needs the `admin` resource.

## Uploads

### Create a Signed Upload [#createsignedupload]

Hand the browser presigned PUT URLs so it can upload files straight to your bucket — no bytes pass through your server. Nothing is written to the database here: each entry carries a signed `token`, and the asset row is created by [`completeUpload`](#completeupload) once the PUT has landed. PUT each file to its `signedUrl` with the returned `headers`, pass the tokens to `completeUpload`, then flip the assets to `public` when you're ready to serve them. New uploads are stored at the object key `<id>/<slug>`.

<APIMethod
  method="POST"
  path="/media/createSignedUpload"
  fn="createSignedUpload"
  collection="media"
  resource="media"
  operation="create"
  args={`{
  body: {
    files: [{ name: 'hero.jpg', size: 512000, type: 'image/jpeg' }], // required
  },
}`}
  returns={{
    uploads: { type: '{ id, objectKey, url, signedUrl, headers, multipart, token }[]', description: 'One entry per file: the asset id and object key it will get, its presigned `signedUrl` (`null` for a multipart upload), the `headers` to send with the PUT, the `multipart` plan (`{ uploadId, partSize, partCount }` or `null`), and the `token` to pass to `completeUpload`.' },
    expiresAt: { type: 'Date', description: 'When the signed URLs expire.' },
  }}
  params={{
    files: { type: '{ name: string; size: number; type: string; variantOf?: string; sha256?: string }[]', required: true, description: 'Files to upload (at least one). `size` is the byte length, `type` a MIME type, `variantOf` an existing asset id when uploading a variant, `sha256` the base64 SHA-256 of the bytes. When the storage verifies checksums on PUT (`checksum.sha256Put`), the hash is signed into the URL (`x-amz-checksum-sha256`) and stored on the asset; otherwise it is ignored.' },
    folderId: { type: 'string', description: 'Target folder id.' },
  }}
/>

Returns `{ uploads: { id, objectKey, url, deliveryUrl, signedUrl, headers, multipart, token }[], expiresAt }`. `url` is `null` (new assets are private); `deliveryUrl` is the gate path. PUT each file to its `signedUrl` with the returned `headers` (`Content-Type`, `Cache-Control`); `expiresAt` is when the signed URLs expire. The token stays valid for one hour past `expiresAt`, so a PUT that started before expiry can still be completed. Throws `TOO_MANY_FILES`, `FILE_TOO_LARGE`, `INVALID_FILE_TYPE`, `FOLDER_NOT_FOUND`, or `ASSET_NOT_FOUND` (unknown `variantOf`).

A file larger than `media.multipart.threshold` (64 MiB) on a storage with the `multipart` capability starts a multipart upload instead: its entry has `signedUrl: null` and `multipart: { uploadId, partSize, partCount }`. Upload part `n` (1-based, `partSize` bytes, the last one shorter) to a URL from [`signUploadParts`](#signuploadparts) and pass the same `token` to `completeUpload`, which assembles the parts. The token of a multipart upload stays valid for 24 hours, so an interrupted upload can be resumed with [`listUploadParts`](#listuploadparts). Parts are 8 MiB unless the file needs larger ones to stay below 9,000 parts.

Before signing, the CMS normalizes each file name (see [Upload security](/docs/guides/media-uploads#upload-security)), checks `media.uploadRateLimit` per actor (`RATE_LIMITED`, 429 with `Retry-After`) and `media.quota` (`QUOTA_EXCEEDED`, 413), and refuses SVG with `INVALID_FILE_TYPE`. Each `token` redeems only at `completeUpload` and only on the host that signed it.

### Complete an Upload [#completeupload]

Create the asset rows for the files the browser PUT to the URLs from `createSignedUpload`. For a multipart upload the CMS first lists the parts the storage holds, checks that every planned part is there with its exact length (`UPLOAD_NOT_FOUND` otherwise) and assembles them. For each token the CMS checks the signature, the calling user and scope, that the token was signed for `completeUpload` on this host, `HEAD`s the object (its length must equal and its content type must match the declared file), sniffs its first 4,100 bytes (markup is refused, image, video, audio and PDF types must match their signature), mints the slug, and inserts the row as `private`. An object that fails the length, type, or sniff check is deleted from the bucket. Completing the same token twice returns the existing asset. One file's failure never fails the call: it is reported per entry in `errors`.

<APIMethod
  method="POST"
  path="/media/completeUpload"
  fn="completeUpload"
  collection="media"
  resource="media"
  operation="create"
  args={`{
  body: {
    uploads: signed.uploads.map(({ token }) => ({ token })), // required
  },
}`}
  returns={{
    assets: { type: 'AssetListItem[]', description: 'The created assets, with the same fields a `listAssets` row carries.' },
    errors: { type: '{ index: number; code: string; message: string }[]', description: 'One entry per rejected token; `index` is its position in `uploads`.' },
  }}
  params={{
    uploads: { type: '{ token: string; hints?: { metadata?, provenance? } }[]', required: true, description: 'The tokens from `createSignedUpload`, at least one and at most `maxFiles`. `hints` are untrusted descriptions from the client (the media-optimize worker): only `metadata.placeholder`, `dominantColor`, `exif` and `media` are kept, validated like `updateAsset`.' },
  }}
/>

For images, the server reads the first 256 KB of the object and stores `width` and `height` from the header, and `provenance` from the XMP `Iptc4xmpExt:DigitalSourceType` or a C2PA manifest (an AI action in the manifest means at least `ai_edited`). A `provenance` hint only counts when the bytes say nothing and the hint is `ai_generated` or `ai_edited`.

Returns `{ assets, errors }`. Per-entry `code` is one of `UPLOAD_TOKEN_INVALID` (malformed, expired, or minted for another user or tenant), `UPLOAD_NOT_FOUND` (no object at the key: the PUT never completed), `VALIDATION_ERROR` (the object's length or content type differs from the declared file), `INVALID_FILE_TYPE` (the bytes contradict the declared image type), `FOLDER_NOT_FOUND` or `ASSET_NOT_FOUND` (the folder or `variantOf` target was removed after presign, or the asset from an earlier completion of this token was archived), `UPLOAD_FAILED` (the bucket answered the object check with an error), or `SLUG_GENERATION_FAILED`.

```ts
// Full browser-side upload flow (the `useUploadAssets` hook does this for you).
const signed = await cmsClient.media.createSignedUpload({
  body: { files: [{ name: file.name, size: file.size, type: file.type }] },
});
await fetch(signed.uploads[0].signedUrl, {
  method: 'PUT',
  headers: signed.uploads[0].headers,
  body: file,
});
const { assets, errors } = await cmsClient.media.completeUpload({
  body: { uploads: [{ token: signed.uploads[0].token }] },
});
```

### Commit a Replace [#commitreplace]

Repoints the asset's row at the new object after the browser's PUT to `createSignedReplace`'s `signedUrl` has succeeded — the second half of the browser-callable replace flow. The token names the asset, object key, slug, type and size, and must have been minted for the calling user and scope. Before anything is written the object is `HEAD`ed (its length must equal and its content type must match the token) and a declared image is sniffed against its magic bytes; a mismatching object is deleted. Atomic and TOCTOU-safe like `replaceAsset`: the row is repointed and old variants archived in one transaction, and it keeps every guarantee `replaceAsset` has (including tombstoning the superseded object so it becomes reclaimable — see [Object lifecycle](/docs/concepts/media#object-lifecycle)).

<APIMethod
  method="POST"
  path="/media/commitReplace"
  fn="commitReplace"
  collection="media"
  resource="media"
  operation="update"
  args={`{
  body: {
    token: signed.token, // required — from createSignedReplace
  },
}`}
  returns={{
    asset: { type: 'AssetListItem', description: 'The updated asset (same `id`, new `slug`/`objectKey`/`url`), with the same fields a `listAssets` row carries.' },
  }}
  params={{
    token: { type: 'string', required: true, description: 'The `token` returned by `createSignedReplace`.' },
  }}
/>

Returns `{ asset }` with the same fields a `listAssets` row carries. Committing the same token twice returns the already-repointed asset. Throws `UPLOAD_TOKEN_INVALID` (malformed, expired, or minted for another user or tenant), `UPLOAD_NOT_FOUND` (no object at the token's key: the PUT never completed), `FILE_TOO_LARGE` / `INVALID_FILE_TYPE` / `TOO_MANY_FILES` (the token's type or size fails the media config as it is at commit time, or the bytes contradict the declared image type), `VALIDATION_ERROR` (the object's length or content type differs from the token), or `ASSET_NOT_FOUND` if the asset was archived or left scope since `createSignedReplace` (TOCTOU) — the row is left unchanged and the just-uploaded object is tombstoned for reclaim rather than abandoned.

```ts
// Full browser-side replace flow.
const signed = await cmsClient.media.createSignedReplace({
  body: { assetId: hero.id, file: { name: file.name, size: file.size, type: file.type } },
});
await fetch(signed.signedUrl, { method: 'PUT', headers: signed.headers, body: file });
const { asset } = await cmsClient.media.commitReplace({
  body: { token: signed.token },
});
```

The client's upload queue runs this pipeline with retries, progress and abort: `await client.media.useUploadAssets().replace(assetId, file, { revisionNote })` resolves with the entry (`kind: 'replace'`). `client.media.useReplaceAsset()` returns only the replace entries with `isReplacing`, `replace`, `abort` and `retry`. The vanilla client runs replaces through the same queue atom, `client.media.uploadState`. See [Upload and serve media](/docs/guides/media-uploads#upload-from-the-browser).

## Downloads

### Sign Downloads [#downloadintent]

Signs short-lived download URLs for assets the caller can read. Each URL is valid for 5 minutes and bound to an attachment disposition named after the asset's original name, so the browser saves the file under that name. With `variantKey` the matching live rendition is signed instead; assets without one are skipped. The React media library uses it to stream several assets into one ZIP archive in the browser, signing small batches just before fetching them.

<APIMethod
  method="POST"
  path="/media/downloadIntent"
  fn="downloadIntent"
  collection="media"
  resource="media"
  operation="read"
  args={`{
  body: {
    assetIds: ['ast_1', 'ast_2'], // required
    variantKey: 'w1280.webp',
    bulkJobId: 'dl_42',
  },
}`}
  returns={{
    items: { type: '{ id: string; url: string; size: number; name: string }[]', description: 'One signed URL per asset that could be signed, in input order, with the stored size and the download name.' },
    skipped: { type: 'string[]', description: 'Ids that are not live in scope or have no rendition with `variantKey`.' },
    expiresAt: { type: 'string', description: 'When the URLs expire (ISO date-time).' },
  }}
  params={{
    assetIds: { type: 'string[]', required: true, description: '1 to 100 asset ids.' },
    variantKey: { type: 'string', description: 'Sign this rendition (e.g. `w1280.webp`) instead of the original.' },
    bulkJobId: { type: 'string', description: 'Groups the calls of one archive download in `onAssetDownload`.' },
  }}
/>

Every signed asset counts against `media.downloadRateLimit` (default 60 per actor and minute, counted per server process); past it the endpoint answers `RATE_LIMITED` (429) with a `Retry-After` header. `media.onAssetDownload` receives `{ assetIds, actorId, variantKey, bulkJobId, ipHash }` after each call. Throws `STORAGE_UNSUPPORTED` when the storage cannot sign reads with a content disposition.

### Export a ZIP Archive [#createzipexport]

Writes a ZIP archive of assets on the server, for downloads the browser cannot assemble itself: archives above its memory cap (2 GB, 500 MB on iOS), 500 files and more, or Safari on iOS. The archive holds the originals of live, `ready` assets in the caller's scope, uncompressed, under their download names; folders become directories unless `flatten`, names are made safe and unique per directory (` (2)`, ` (3)`) like a browser download, and `manifest` adds `manifest.csv` (`id,path,size,usage`, usage counting the live pages). The archive is written to `exports/<id>/<name>` in parts of 8 MiB and is downloadable for 24 hours.

<APIMethod
  method="POST"
  path="/media/createZipExport"
  fn="createZipExport"
  collection="media"
  resource="media"
  operation="read"
  args={`{
  body: {
    assetIds: ['ast_1', 'ast_2'],
    name: 'campaign',
    manifest: true,
  },
}`}
  returns={{
    export: { type: 'MediaZipExport', description: 'The export as `getZipExport` returns it, `pending` at first.' },
  }}
  params={{
    assetIds: { type: 'string[]', description: 'Up to 10,000 asset ids; or pass `allMatching`.' },
    allMatching: { type: '{ query: Record<string, unknown>; except?: string[] }', description: 'A `listAssets` filter resolved on the server instead of `assetIds`.' },
    name: { type: 'string', description: 'Archive file name; `.zip` is appended when missing. Default `media`.' },
    flatten: { type: 'boolean', description: 'Put every file at the top level.' },
    manifest: { type: 'boolean', description: 'Add `manifest.csv`.' },
  }}

The work runs in the background through `media.runExport` (see [Configuration](/docs/reference/configuration#media)), and the [pruning pass](/docs/reference/admin#runpruning) continues every unfinished export at its last stored part, so an export survives a serverless function that is stopped early. When it finishes, the realtime channel of the scope gets `media.export.ready` (or `media.export.failed`) with `{ exportId }`. An asset whose object is missing or has another length when its turn comes is left out and listed in `skipped`. `media.onAssetDownload` receives the asset ids with the export id as `bulkJobId`. Throws `RATE_LIMITED` (429) when the caller already has 3 unfinished exports, and `STORAGE_UNSUPPORTED` when the storage cannot write multipart uploads or sign reads with a content disposition.

## Public delivery

### Serve an Asset [#asset]

Address an asset by its **id** (what content stores); the gate `302`s to the asset's current object. It's what you put behind an `<img src>`, and it survives a `replaceAsset` untouched: the gate re-resolves the id to the current object. A public asset redirects to its object URL, short-cached (`max-age=300`, not immutable), so swapping the object behind the same id propagates automatically. A private asset redirects to a signed GET valid for at most 300 seconds with `Cache-Control: private, no-store`, and only for a caller your `authMiddleware` accepts for `media` / `read`; anonymous callers get `ASSET_ACCESS_DENIED`. With a scoping plugin, ids outside the caller's scope answer `ASSET_NOT_FOUND`.

<APIMethod
  method="GET"
  path="/media/asset/{assetId}"
  fn="asset"
  collection="media"
  public
  args={`{
  params: { assetId: 'ast_123' }, // required
  query: { w: 800, format: 'webp' },
}`}
  returns={{
    Location: { type: '302 redirect', description: "A `302` (short-cached, `max-age=300`) to the asset's public object URL for raster images (PNG, JPEG, GIF, WebP, AVIF), video, audio and PDF, or, for `download=true` and every other type, to a signed object URL valid for one hour whose `response-content-disposition=attachment` makes the bucket answer with a download. No JSON body: the browser follows the `Location` header to the bytes." },
  }}
  params={{
    assetId: { type: 'string', required: true, description: 'Path parameter: the asset id to serve.' },
    format: { type: "'webp' | 'avif' | 'jpeg' | 'png'", description: 'Rendition format (default `webp` when `w` is given).' },
    w: { type: 'number', description: 'Rendition width. Snaps up to the next of `renditionWidths` (default 320, 640, 1280, 1920); larger than the largest answers `RENDITION_WIDTH_UNSUPPORTED`.' },
    strict: { type: 'boolean', description: 'Answer `RENDITION_NOT_FOUND` instead of serving the original when no rendition fits.' },
    download: { type: 'boolean', description: 'Set `true` to redirect to a signed URL that forces a download (`Content-Disposition: attachment`, filename = the asset slug) instead of the public object URL.' },
  }}
/>

With `w` or `format`, the gate serves a **rendition** and says which in the `x-cms-rendition` header: `exact` (the variant with that `variantKey`, e.g. `w640.webp`), `nearest` (the smallest larger rendition of the same format) or `miss` (none fits: the original is served and `onRenditionMiss` is called). It never guesses a width that does not exist. Include `w`, `format`, `download` and `strict` in your CDN cache key (no `Vary: Accept`: the format is in the URL). The gate calls `onPurge` with `/media/asset/<id>` after a replace, archive, status change or new rendition.
