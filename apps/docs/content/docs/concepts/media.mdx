Media (images, video, PDFs) lives in object storage (S3, Cloudflare R2, DigitalOcean Spaces, or any S3-compatible bucket), with one row per asset in the CMS database. The CMS handles uploads, access control, folders, and variants; serving happens from your bucket or a CDN. For exact method signatures, see the [media reference](/docs/reference/media).

## The asset model

Each upload creates a row in `assets`:

| Field | Meaning |
| --- | --- |
| `id` | Stable primary key (`ast_…`). What content stores and what the gate resolves. Never changes, even when the bytes are replaced. |
| `slug` | Unique, URL-friendly name derived from the filename. Regenerated on `replaceAsset`. |
| `objectKey` | The key in your bucket: `{tenant}/{pub or prv}/<id>/<slug>` (see [Private vs public](#private-vs-public)), where the id is fresh per upload, replace and move. |
| `status` | `'private'` (default) or `'public'`. |
| `folderId` | The folder it lives in, if any. |
| `variantOf` | If set, this asset is a variant (a resized or reformatted copy) of another. |
| `mimeType`, `size` | Content type and byte size. |
| `archivedAt` | Soft-delete marker for pruning. |

Three of these are identifiers, and keeping them straight is the key to the whole model. The `id` is stable and opaque: content references it, and the gate is addressed by it. The `slug` is a human-readable name derived from the filename, unique within a scope (two tenants can both own `hero.jpg`); the `objectKey` is where the bytes live in your bucket and ends in the slug. The `id` and the slug/key pair are decoupled on purpose. [`replaceAsset`](/docs/reference/media#replaceasset) (server-side) or [`createSignedReplace`](/docs/reference/media#createsignedreplace) + [`commitReplace`](/docs/reference/media#commitreplace) (browser) mints a new slug and object key for the new bytes but keeps the `id`, so every reference follows the swap while the CDN still treats each version's object as immutable.

Folders are a nested tree (`asset_folders`, each with a `parentId`). They organize the media library and nothing more: a folder does not affect an asset's URL, its status, or how it is served. [`listFolders`](/docs/reference/media#listfolders) reads one level at a time (the children of a parent, or the root-level folders when no `parentFolderId` is given); [`createFolder`](/docs/reference/media#createfolder), [`moveFolder`](/docs/reference/media#movefolder), and [`deleteFolder`](/docs/reference/media#deletefolder) manage them. A folder that still holds assets or subfolders cannot be deleted (it throws `FOLDER_HAS_CONTENT`), and moving an asset carries its variants along, so an original and its variants are never split across folders.

## Private vs public [#private-vs-public]

`status` decides who can read an asset's bytes. An asset is created `private`. Publishing content that references it flips it to `public`, and unpublishing reverts it to `private` unless another published page still references it; [`updateAssetsStatus`](/docs/reference/media#updateassetsstatus) sets it by hand.

With the default `media.visibility: 'prefix'`, the status is also where the object lives:

- `pub/<id>/<slug>` for public assets, `prv/<id>/<slug>` for private ones. Under the multi-tenant plugin the tenant comes first: `t/<tenant>/pub/...`.
- The bucket itself is private. A bucket policy grants anonymous reads on `pub/*` only, so public bytes stay CDN-cacheable without a signature per request, while private bytes are reachable through the gate alone.
- A status change moves the object (and its variants) by **copy plus delete**: copy to the new prefix, update the row's status and `objectKey` in one transaction, then delete the old object. If the copy fails, status and keys stay unchanged. `media.onPurge` receives the gate paths to purge from your CDN afterwards. Moving a large video costs a copy of its bytes.
- No `x-amz-acl` header is ever sent.

The storage must support `copy`; `createCMS` throws at construction otherwise. Objects uploaded before you switched to `prefix` keep their keys until their next status change moves them.

`media.visibility: 'legacy'` keeps keys without a visibility segment and never moves objects. There `private` only stops the gate from serving an asset; anyone who knows the key can read it from the bucket unless you lock the bucket down yourself. With `legacy`, `media.acl: 'public-read'` sends `x-amz-acl: public-read` on providers that support object ACLs.

<Callout type="warn">
With `visibility: 'legacy'`, `private` is not an access boundary. Use `prefix` for files that must stay private.
</Callout>

As defense in depth, serve assets from a **cross-origin** host (a `publicUrl` that is not your app's origin) so an uploaded file cannot run as same-origin, and note that the default `allowedMimeTypes` excludes SVG for the same reason. See [Security: Media privacy](/docs/resources/security#media-privacy).

## Uploading: signed URL vs server

Two upload paths write the same rows and enforce the same limits; they differ only in who holds the bytes:

- **[`createSignedUpload`](/docs/reference/media#createsignedupload) + [`completeUpload`](/docs/reference/media#completeupload) (default).** `createSignedUpload` returns presigned PUT URLs and a signed token per file without writing a row; the browser uploads each file straight to the bucket; `completeUpload` verifies each landed object (length, content type, and the magic bytes of a declared image) and only then creates the row. No file bytes pass through your server, so there are no serverless body-size limits and less egress. A PUT that is never completed leaves an object in the bucket but no row, so it never appears in the library; [`abortUpload`](/docs/reference/media#abortupload) deletes it right away, and the [pruning sweep](/docs/concepts/data-retention) removes what nobody aborted. Use this for browser uploads; the React `useUploadAssets` hook wraps all three steps.
- **[`uploadAssets`](/docs/reference/media#uploadassets).** You send the file bytes (a `buffer: Blob | ArrayBuffer` per file) to the CMS, which PUTs them to the bucket. Use this for server-side sources.

Both validate against the limits (defaults: `maxFiles` 10, `maxFileSize` 4 MB, and an `allowedMimeTypes` allowlist that **excludes SVG**; see [Configuration](/docs/reference/configuration#media)), and signed URLs expire after 300s by default. Every new asset lands `private`, so uploading and serving are two steps:

```ts
// Server-side upload: bytes go through the CMS to the bucket.
const { assets } = await cms.api.media.uploadAssets({
  body: {
    files: [
      { name: 'welcome-hero.jpg', size: buffer.byteLength, type: 'image/jpeg', buffer },
    ],
  },
});
const [hero] = assets; // { id: 'ast_…', slug: 'welcome-hero.jpg', status: 'private', … }

// New assets are private. Publishing referencing content flips this for you;
// to serve an asset on its own, make it public explicitly.
await cms.api.media.updateAssetsStatus({
  body: { assetIds: [hero.id], status: 'public' },
});

// Now it serves through the gate, addressed by its id:
//   <img src={`/media/asset/${hero.id}`} />
```

The browser hook is covered step by step in [Upload and serve media](/docs/guides/media-uploads).

### Replacing: signed URL vs server

Swapping an existing asset's bytes has the same two-path split as uploading, for the same reason — a browser cannot send raw file bytes through a JSON request body:

- **[`createSignedReplace`](/docs/reference/media#createsignedreplace) + [`commitReplace`](/docs/reference/media#commitreplace) (browser).** `createSignedReplace` validates the target and mints a signed PUT URL plus a signed token without touching the row; the browser PUTs the bytes straight to the bucket; `commitReplace` takes the token, verifies the landed object the same way `completeUpload` does, and repoints the row. The client upload queue's `replace` (`useUploadAssets().replace`, or the `useReplaceAsset` hook) wraps both calls.
- **[`replaceAsset`](/docs/reference/media#replaceasset) (server-side only).** Takes the file bytes directly (`buffer: Blob | ArrayBuffer`) in one call. A browser `File` cannot survive `replaceAsset`'s JSON body — it serializes to `{}` — so this endpoint is for server-initiated replacements only.

Both mint a fresh slug and object key (the cache-bust) and keep the asset's `id` stable, exactly like `replaceAsset` described above.

## Serving assets

Serve assets through the **gate**: [`GET /media/asset/{id}`](/docs/reference/media#asset), a public redirect to the object, addressed by the **asset id** (which is what content stores). It is the contract to use in content and on public pages. It enforces `status` (a `private` asset returns `ASSET_ACCESS_DENIED`) and honors `?format=webp|jpeg|png` and `?w=<width>` by resolving a **pre-uploaded variant**, falling back to the original.

There is no on-the-fly transform. A variant is just another asset row whose `variantOf` points at the original and whose `slug` is derived from the original plus the requested format and width. The gate computes that expected slug and looks it up: a hit is served, a miss silently serves the original. So a request for `/media/asset/{id}?w=800&format=webp` on an asset stored as `welcome-hero.jpg` resolves to a sibling asset named `welcome-hero-800-webp.webp`:

```ts
// Register a pre-sized WebP variant of an existing asset.
await cms.api.media.createSignedUpload({
  body: {
    files: [
      {
        name: 'welcome-hero-800-webp.webp', // matches the slug the gate derives
        size: variantBytes,
        type: 'image/webp',
        variantOf: hero.id,
      },
    ],
  },
});
// GET /media/asset/{hero.id}?w=800&format=webp now serves this variant;
// any other size or format still falls back to the original.
```

Create the variants you need ahead of time. The [media optimize plugin](/docs/plugins/media-optimize) resizes and re-encodes images in the browser before upload, so the stored bytes are already small.

`?download=true` redirects to a short-lived **signed** object URL (valid for one hour) that carries `response-content-disposition=attachment` bound into the signature, so the bucket answers with a `Content-Disposition` header and the browser downloads the file under its slug; a `Content-Disposition` header on the `302` itself would be ignored by browsers. Types outside the raster-image (PNG, JPEG, GIF, WebP, AVIF), video, audio and PDF set are always served that way, so an allowed SVG or HTML asset never renders inline from the gate even if `allowedMimeTypes` admits it.

The redirect for a public asset is **short-cached** (`public, max-age=300`, not immutable). Because it is keyed by the stable id, swapping the bytes behind that id re-resolves and propagates to already-rendered pages within minutes, while the object bytes stay long-cached at the CDN, since each version has its own object key.

A **private** asset is served only to a caller your `authMiddleware` accepts for the `media` resource with `read`, inside its scope: the gate redirects to a signed GET valid for at most 300 seconds, with `Cache-Control: private, no-store` on the redirect. Anonymous callers get `ASSET_ACCESS_DENIED`. With a scoping plugin, a caller whose middleware resolves a tenant only reaches that tenant's assets; other ids answer `ASSET_NOT_FOUND`.

<Callout type="warn">
  Deployment note: a CDN in front of the gate must include the **query string** in its cache key (`w`, `format` and `download` at least). The redirect target differs per `?format`, `?w`, and `?download`, and only the query string distinguishes those cache entries. If the CDN strips it (for example a Cloudflare "ignore query string" cache rule), the variant, download, and original redirects collapse into one and get cross-served.
</Callout>

Every asset returned by [`listAssets`](/docs/reference/media#listassets) and the upload responses carries `deliveryUrl`, the gate path (`{basePath}/media/asset/{id}`); render that. `url`, the direct object URL `${publicUrl}/${objectKey}`, is set only for public assets and is `null` for private ones. It bypasses the gate (no status check, no transforms), so do not bake it into content.

## Images in content

An `image` block property stores the asset **id** (an `ast_…` reference), never a URL, and the read path returns it verbatim (nothing is resolved). Your renderer builds the gate URL straight from that id: `<img src="/media/asset/{id}">`. Because the id is stable, swapping the object behind it updates every reference automatically, with no content change and no re-render. Do not store the direct `url` in content: it bypasses the status gate and transforms, pins the entry to your bucket layout, and will not follow such a swap.

[`getAssetUsages`](/docs/reference/media#getassetusages) reports which entries reference an asset (the index keys on the asset id), and archiving is blocked while an asset is used by live content:

```ts
// Which live pages reference this asset?
const { pageCount, pages } = await cms.api.media.getAssetUsages({
  query: { assetId: hero.id },
});
```

## Object lifecycle [#object-lifecycle]

Archiving an asset ([`archiveAssets`](/docs/reference/media#archiveassets)) is soft-delete: the row gets `archivedAt` set and drops out of `listAssets`/the gate, but the row and its S3 object both stay put until a later [pruning pass](/docs/concepts/data-retention) reclaims them — once it is past the trash window (`archiveKeepDays`) and no live content references it.

Replacing an asset (either path above) mints a *new* object for the new bytes but keeps the row's `id`, so the row that used to name the *old* object no longer exists after the swap — nothing would ever reference the superseded object for reclaim. To close that gap, a replace also inserts a **tombstone**: a fresh, already-archived asset row that reuses the *old* slug/object key (with a brand-new `id`, never referenced by any content). That tombstone is what the pruning pass actually finds and reclaims once its trash window elapses — so a superseded object is not left behind forever, and replacing the same asset repeatedly does not accumulate orphaned bytes in your bucket.

## Storage adapters [#storage-adapters]

Objects are stored in an S3-compatible bucket by default (`provider` picks AWS, DigitalOcean Spaces, Cloudflare R2 or a custom endpoint). Set `media.storage` to a `StorageAdapter` to use another backend; every storage operation then goes through it, while public URLs still come from `media.publicUrl`.

An adapter declares its `capabilities`, and the media routes check them before any I/O; an operation the adapter does not declare fails with `STORAGE_UNSUPPORTED` naming the capability. `signedPut.supported` gates `createSignedUpload` / `createSignedReplace`, `rangeRead` is required to verify an uploaded image's bytes, `signedGet` (with `disposition` for downloads) backs the gate's signed redirects, and `copy` is required for `visibility: 'prefix'`. `list` and `deleteMany` are optional. `createS3StorageAdapter(mediaConfig)` builds the default adapter, and backend failures thrown as `StorageError` map to a 500.

The S3 adapter takes its capabilities from a preset per provider (`providerCapabilities`); a custom endpoint picks one with `preset`, and `media.capabilities` overrides single flags:

| Preset | Notes |
| --- | --- |
| `aws` | Everything, including POST policies and object ACLs (on buckets that still allow ACLs). |
| `r2` | No POST, no object ACLs; lifecycle rules; presigning only on the S3 API domain, 1 second to 7 days. |
| `b2` | No POST, no object ACLs. |
| `doSpaces` | Canned ACLs; lifecycle for incomplete multipart uploads. |
| `hetzner` | Object ACLs, lifecycle; 5 GB per single PUT, 750 requests/s per bucket and IP. |
| `bunny` | CORS fixed to `*`, no lifecycle; 500 requests/s. |
| `supabase` | No CORS configuration through S3, no Content-MD5. |
| `generic` | The S3 core (default for `provider: 'custom'`). |

```ts
media: {
  provider: 'custom',
  preset: 'hetzner',
  hostname: 'fsn1.your-objectstorage.com',
  region: 'fsn1',
  capabilities: { signedGet: { maxExpiresIn: 3600 } },
  // ...
}
```

## Bucket setup [#bucket-setup]

Run `createcms storage check --origin https://admin.example.com` after configuring a bucket. It checks the capabilities, the lifecycle rule, the CORS preflight from your admin origin, an upload without ACL headers and, with `visibility: 'prefix'`, that `publicUrl` serves `pub/` but not `prv/`. Each failed check prints a configuration to paste.

**Bucket policy.** Grant anonymous reads on `pub/*` only (AWS; R2 exposes a public bucket through a custom domain, so point that domain's access at `pub/` or put the CDN in front of `pub/` only):

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "PublicReadPub",
      "Effect": "Allow",
      "Principal": "*",
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::my-bucket/pub/*"
    }
  ]
}
```

**CORS.** Browser uploads PUT from your admin origin with `content-type` and `cache-control` (add `x-amz-checksum-sha256` if you sign checksums); ZIP downloads GET from the same origin. `x-amz-acl` is not needed. AWS and Hetzner (`aws s3api put-bucket-cors`):

```json
{
  "CORSRules": [
    {
      "AllowedOrigins": ["https://admin.example.com"],
      "AllowedMethods": ["PUT", "GET"],
      "AllowedHeaders": ["content-type", "cache-control"],
      "MaxAgeSeconds": 3600
    }
  ]
}
```

Cloudflare R2 (bucket settings, CORS policy):

```json
[
  {
    "AllowedOrigins": ["https://admin.example.com"],
    "AllowedMethods": ["PUT", "GET"],
    "AllowedHeaders": ["content-type", "cache-control"],
    "MaxAgeSeconds": 3600
  }
]
```

Send `Vary: Origin` on GET responses from your CDN when the admin origin downloads through it.

**Cache-Control.** Every object is written with `Cache-Control: public, max-age=31536000, immutable` (private objects under `prefix`: `private, max-age=31536000, immutable`). Object keys are unique per upload, replace and move, so no object ever changes.

**nosniff.** S3 cannot set `X-Content-Type-Options` per object. Add `X-Content-Type-Options: nosniff` as a response header at your CDN: a CloudFront response headers policy, a Cloudflare Transform Rule (modify response header), or a Bunny Edge Rule.

**Lifecycle.** Where the provider has a lifecycle API, add a rule that aborts incomplete multipart uploads after 1 to 7 days (R2 defaults to 7 days):

```json
{
  "Rules": [
    {
      "ID": "abort-incomplete-multipart-uploads",
      "Status": "Enabled",
      "Filter": { "Prefix": "" },
      "AbortIncompleteMultipartUpload": { "DaysAfterInitiation": 7 }
    }
  ]
}
```

## Limitations

The media pipeline is deliberately thin. Know these boundaries before you design around it:

- **No server-side image transforms.** `GET /media/asset/{id}?format=webp&w=800` resolves a **pre-uploaded variant** (an asset whose `variantOf` points at the original) by matching the requested format and width. If no matching variant exists, the gate **silently serves the original**, at its stored size and format: an unmatched `?format` or `?w` is not an error and does not resize or convert on the fly. Create the variants you need ahead of time.
- **Optimization is client-side only.** The [media optimize plugin](/docs/plugins/media-optimize) resizes and re-encodes each image **in the browser** (via a canvas) before upload, then uploads the smaller result. Nothing optimizes server-side, so a file uploaded through a path that skips the plugin is stored as-is.
- **Assets store bytes and status, nothing else.** An `assets` row carries the fields in the table above and no more. There is no stored **width/height**, **focal point**, **alt text**, or **caption**. Keep intrinsic dimensions, art-direction focal points, and accessibility text on your content instead (for example an `image` block's own `alt` property), not on the asset.
